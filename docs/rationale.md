## 共用制度副本

2026-11-14 使用者決定把部署包的共用制度逐字貼進本 repo 的 `AGENTS.md`。全域 `~/.claude/skills/handoff/` 換成 v3 之後，skill 把必守條件與 session 命名都指向 `AGENTS.md` 的共用制度；本 repo 刻意沒有專案層 skill，`AGENTS.md` 要是沒有那一節，接棒時就找不到命名規則。只加一行指標太依賴模型自己去讀，貼入則由 `CLAUDE.md` 的 `@AGENTS.md` 自動載入。

代價與守門：`sync_project.py` 拒絕本 repo，副本只能手動重貼；`verify_bootstrap.py`「規則理由連結」要求它跟 `src/kit/files/AGENTS.md.tmpl` 逐字相同，並只對兩個標記之間跳過死連結與理由連結檢查（副本連到部署後才存在的 skill 路徑），標記壞掉就不跳。

共用制度裡各條條件本身的理由在部署包 handoff skill 的 `reasons.md`（本機讀全域 `~/.claude/skills/handoff/reasons.md`；沒有全域副本時看範本 [src/kit/files/.claude/skills/handoff/](../src/kit/files/.claude/skills/handoff/reasons.md.tmpl)）與需求決策書 v3，這裡不重抄。

## 跟部署出去的專案不同的地方

這一節寫在 `AGENTS.md` 而不只放開場 hook，是因為有些工具不跑 hook（還沒被信任的 Codex 就不會跑），而 `AGENTS.md` 是每個工具都保證會讀到的入口；只放在 hook 裡，這些事實會在一部分工具上無聲消失（2026-11-01 補：部署包範本一直有這一節，缺的反而是來源自己）。

2026-11-14 起這一節照需求決策書 v3 D12 只寫事實，不寫逐步程序：同步與開工標記的義務已由共用制度的不可違反條件承載。寫進來的事實都是踩過才知道的：驗證入口是 `verify_bootstrap.py` 而不是骨架的 `verify_state.py`；`--staged` 拒絕未暫存與未追蹤檔，免得用工作樹的結果證明另一份提交候選；這台 Mac 沒有 `python`，所以寫 `python3`；本 repo 沒有專案層 skill，沒有全域副本的乾淨機器要讀部署包 3.8 節，2026-11-10（F16a）乾淨 clone 加空家目錄實測時，舊句叫人開一個不存在的檔。

## 這個 repo 是什麼

**這裡是制度的來源，不是知識庫。** 對外的產出物 2026-11-18 起是安裝程式 `bootstrap.py`（v3 Q49）：舊做法要 AI 讀進約 200KB 的部署包、再逐字輸出二十幾個檔，輸出最貴也最容易抄錯，部署包第 4、5 節的驗收就是在補這個洞；同類專案（GitHub Spec Kit、BMAD Method、Agent OS）都是程式寫檔、裝好後由 agent 補專案專屬的內容。專案知識、踩坑紀錄與狀態屬於各自的專案 repo；不部署的東西只有本 repo 的檢查與測試（`tools/verify_bootstrap.py`、`src/project_bootstrap/`、`tests/`、`tools/run_tests.py`，只用合成 fixture，v3 Q46）、開發骨架與 `HANDOFF.md`。

**`HANDOFF.md` 是例外**：2026-10-30 起多機維護，`git log` 與 `git fetch` 看不到別台機器未提交的變更，所以補上跨機器「工作中」標記，沿用範本 3.3 的載體與 3.10 讀的同一個欄位，不發明第二種標記。它同時必須是可信的當下快照：2026-11-01 發生過規則只要求改標記、舊待辦整批凍結的事故（見[本 repo 的交接快照](#snapshot)）。標記只說「東西在那台機器上」，東西本身仍得回那台 push。

**刻意沒有 handoff skill 與 `check_docs.py`**：把骨架的副本裝到來源自己身上，會出現權威版與副本互相同步的迴圈。2026-11-06 使用者選擇照 D4／F34 把這兩項宣告為例外（F46 要求來源的保護不低於產物，允許補裝或宣告）；宣告不等於 F46 已達成，撤銷宣告是使用者的決定。

**push 前 hook 2026-11-14 補裝**（`repo-pre-push.sh`）：v3 的 F10 是唯一保留「阻擋」的需求，擋的是沒寫開工標記就推權威分支；來源少這一層，就違背 F46。之前不裝的理由是它攔不住「檔案改了、待辦沒改」的事故，v3 把它的保證收窄成只擋沒寫標記的推送，那個理由就不再成立。開場與 push 前兩支 hook 都是部署包的逐字副本，不經 `sync_project.py`：同步器靠 handoff skill 發現專案，`--all` 掃不到本 repo（見[副本規則 7](#copy-7)）。

## 鐵律 1

**權威只有一個家。** 在單一專案就地改 skill 或 hook，就是「同一個事實有多個家」的失控起點；改了要經部署包發出去。2026-11-11（P1 第三片）權威從手改的 `PROJECT-BOOTSTRAP.md` 搬到 `src/kit/`：一份 28 萬位元組的檔案夾著 27 個範本，範本無法單獨 diff 或測試。2026-11-18 起各專案跑的是 `bootstrap.py`（v3 Q49），`update` 用的合併函式原樣取自 `sync_project.py`，所以安裝、更新與同步只有一套邏輯。同日 `PROJECT-BOOTSTRAP.md` 退休（v3 Q50）：它是範本的第二份副本，提交著就得一直保持同步；驗證器與同步器改成在記憶體組出全文，同步器認得的「已發布版本」來自它的 Git 歷史與 `bootstrap.py` 的歷史。手改 `bootstrap.py` 或把部署包放回來都會被擋（「安裝程式由來源生成」「部署包由來源生成」）。

**`VERSION` 只跟 handoff skill 目錄走。** 各專案的開場檢查拿 skill 檔頭的 `source:` 標記比上游 `VERSION`；只改了不同步的範本就跳版，每個專案會永遠印「骨架落後」，而且同步修不掉（2026-10-30 踩到）。2026-11-10 skill 拆成目錄後，目錄裡所有檔的標記要同版：開場只讀入口那一行，模式檔落後時不會有提示。

**跳版不會立刻提示**：開場 hook 把上游版本快取 720 分鐘，要下一次開場就提示，刪掉那個專案的 `.claude/.bootstrap-version`（2026-11-01 六個專案的快取停在舊版，決定整晚沒生效）。

<a id="rule-2"></a>

## 鐵律 2

`source:` 標記是分辨哪份副本落後的唯一依據。2026-10-24 同一天改了三次而標記三次相同，副本落後卻顯示一樣新，誤判成同步漏掉，白查一輪；所以同一天第二次起加序號。序號算當天第幾個帶標記的改動，跟部署包「版本」行不保證同號：版本行只跟 handoff skill 目錄走（鐵律 1），當天後續沒動到 skill 的改動會讓標記超前版本行（2026-11-02／F15 統一說法）。

## 鐵律 3

這份骨架的價值不在條文，在條文背後的事故；砍掉理由，下一棒就會繞過規則（2026-08-05 隨首版寫入）。2026-11-10（F22）理由從入口搬到理由檔之後，`verify_bootstrap.py`「規則理由連結」擋沒有理由的規則；2026-11-18（v3 Q48）起理由檔只留現行理由，被取代的搬到歷史紀錄，仍然不刪。

## 鐵律 4

2026-08-05 之前驗證是要人照著手刻的敘述，每一棒都得重刻，實務上常被跳過，所以固化成一個指令；它檢查什麼見 [ARCHITECTURE](../ARCHITECTURE.md) 的「`tools/verify_bootstrap.py` 守的東西」。印 `skip` 的項目沒有被驗證，所以回傳 1。2026-11-14 加 `--quiet` 只隱藏成功明細，FAIL／SKIP 與結束碼不變；測試套件改成子程序與其他檢查重疊，不快取、不省略，縮短的是等待，不是證據。

## 鐵律 7

2026-11-18（需求決策書 v3 Q43，使用者決定）：這個 repo 由不同的 session、模型、機器輪流做，每一棒都可能覺得「這樣比較好」而偏離需求，而且要做完才會發現。原本的規則只規定文件各寫什麼，沒規定執行要照著走，所以提升成開工時會讀到的鐵律。

- **只有使用者能改**：如果 AI 自己就能改文件，「先改文件再偏離」就等於拿一個 commit 給自己授權，這條規則形同虛設。
- **計畫只約束到分期、範圍、暫緩與取捨**：如果每一步都得照計畫走，換個實作方式也要先改計畫，文件會一直被改，反而沒人當真。
- **衝突時停下來**：共用制度本身就來自決策書，兩邊衝突代表其中一邊漏改了；自己挑一邊照做，會讓錯的那邊一直留著。
- **驗證器管不到執行**：它只能檢查這條規則和理由還在，檢查不了某次執行有沒有照文件走。這條主要靠 AI 開工時讀到。

## 副本規則 1

漏覆蓋一份副本，那台機器就繼續照舊制度做事，而且沒有徵兆。選用的全域副本也算：2026-10-30 實測 Codex CLI `0.164.0` 仍讀 `~/.codex/skills/handoff/`，雖然官方文件已經不列這個路徑。

兩份 hook 接線是 JSON，放不了 `source:` 標記，落後偵測看不見它們，唯一的守門人是 `sync_project.py` 的 `WIRING` 清單加上驗證器「同步清單涵蓋骨架」。2026-09-13 給 3.9 補的 `Bash|PowerShell` matcher 就是因為接線不在同步清單裡而一直沒發下去：三個專案停在舊的 `Bash`，而那台機器的主 shell 正是 PowerShell，push 前防呆在那些專案等於沒裝，一個半月沒有任何徵兆；2026-10-30 把接線補進拓撲與同步清單。

## 需求與計畫文件的分工

每份文件各答一個問題，同一件事只寫在一處（2026-11-17 使用者指示）：當時根目錄有 19 份查核、計畫與需求討論檔，結案的跟有效的混在一起，下一棒無從分辨哪份還算數，只能每份都讀。計畫只引用需求 ID，需求改了才不會留下過期的副本（D3 的同一個理由）。

- **權威只寫現況，經過放成對的歷史紀錄**（v3 Q42）：條文夾著修訂經過時，讀的人要自己從經過推算現況，約束文件就沒辦法直接讀。
- **歷史分冷熱兩區**（v3 Q44、Q45）：熱歷史 `docs/history/` 跟現行版本有關、還會增加，碰到就讀；冷區 `archive/` 是結案或被取代的東西，平常不讀、回溯先經使用者同意，冷的東西只有一個家。
- **舊版本名稱的東西退出現行區**（v3 Q46、Q47）：標記成舊版的程式與文字留在現行區，下一棒分不出哪個還在用；換版只要 AGENTS 改連新版決策書，「版本更替」就開始要求清理。
- **規則、做法、理由分三處**（v3 Q48）：`AGENTS.md` 每個 session 自動載入，只寫規則；AI 維護手冊做到那件事才讀，只寫步驟、指令與坑；理由檔只寫現行理由。原本照「什麼時候讀」切成 AGENTS、CONTRIBUTING、AGENTS-reasons，CONTRIBUTING 的名字是業界標準、內容卻不是給外部貢獻者的指南，理由檔又混了理由、事故與舊措辭，定位模糊。

<a id="eol"></a>

## 行末

部署包全檔是 LF；用 Python 改寫時不加 `newline=''`，Windows 會把整份寫成 CRLF（2026-08-05 隨首版寫入）。`.gitattributes` 與驗證器的行末檢查兩邊擋。

<a id="hook-1"></a>

## 改兩支 hook 的訊息時 1

反引號在雙引號裡是命令替換：``echo "格式是 `機器` ／ `工具`"`` 會讓 shell 真的去執行 `機器`，訊息變成空白再加一行 command not found，而那兩支 `.sh` 會被抄進每個專案，錯一次就是錯六份。2026-11-02 修 F01 時當場踩到；驗證器的共用情境表現在把那句訊息的字面寫法釘住了。

<a id="hook-2"></a>

## 改兩支 hook 的訊息時 2

macOS 內建的 `/bin/bash` 3.2 在 UTF-8 語系下，會把緊接 `$變數` 的中文字的第一個位元組吃進變數名，每一句結論訊息都壞掉，而 Windows 的 Git Bash（bash 5）完全不重現。2026-11-06 第一次在 Mac 上跑驗證才以三項 FAIL 現形，修掉部署包 22 處、本 repo hook 17 處；驗證器的「bash 3.2 多位元組變數」靜態掃描現在會擋。

<a id="hook-3"></a>

## 改兩支 hook 的訊息時 3

把 patch 從 heredoc 餵進 `python -` 時，轉義會被多解一層：反斜線 n 變成真的換行、反斜線 t 變成字面上的 TAB，shell 範本的 `printf` 格式字串被切成三行，而這種壞法在 diff 上很難看出來。2026-11-02 同日踩到三次，第三次就是在寫這一條的時候。

<a id="hook-4"></a>

## 改兩支 hook 的訊息時 4

手寫 `\u` 碼點會靜默寫出異體字或錯字：2026-11-05 一天踩兩次，包括 `㊣` 寫成 U+321B（正確是 U+32A3）、`權` 寫成日文異體，兩次在 diff 上都看不出來。patch 腳本加「命中數 ≠ 1 就 abort」，第二次就是靠它擋下來的。
