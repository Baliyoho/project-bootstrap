## 非目標的理由

以下出自實施計畫 v3 第 5 節。

| 非目標 | 理由 |
|---|---|
| 不以永久的平台分支維護多份核心 | Git、占用、文件與同步的判斷要共用，平台差異放模組；兩份各自演化會出現一邊會擋、一邊不會擋的不對稱（出處：效率計畫 7.3、理由檔副本規則 2）〔計畫 §5〕 |
| 不恢復凍結的執行屏障與簽章發布通道 | D9 把執行屏障交給工具；十個以內的專案用不到金鑰鏈〔計畫 §5〕 |
| 不以自動信任 hook、繞過沙箱或搬運憑證換取速度 | D9 把權限與沙箱交給工具原生能力；hook 信任不能以快取代替當下觀測（出處：效率計畫 5.2）〔計畫 §5〕 |
| 不一次重寫所有程式、不先導入框架、不預先宣稱跨作業系統或 Python 下限通過 | 框架增加依賴與載入差異，本專案沒有量測支持（出處：效率計畫 14.7）；Python 下限只有靜態檢查；跨作業系統要等第 3 期（F15）〔計畫 §5〕 |
| F22 不另設時間上限 | F22 只照 D11 的行數預算〔計畫 §5〕 |

## 為什麼放在 repo 裡

以下出自原則草稿第 1 節，是 [goal](new_draft/goal.md) 開頭與效用 1 的論證。

過去 repo 主要用來放程式碼版本。現在 repo 裡一定會有、而且不可取代的，是和 AI 協作的系統。這套系統包括專案的規範、結構、進度、決策、交接、歷史等，以及相應的驗證程式。〔原則草稿 §1〕

- 系統包含的東西大多不是全新的，很大一部分本來就是 repo 裡慣有的文件，參與者原本就用它們來管理專案、互相協調。這個目的沒有改變，改變的是參與者從人變成 AI agent。〔原則草稿 §1〕
- 參與者改變了，舊配置就不合時宜：人會把進度和協作規則放在腦中，或放在 repo 外的文件。AI 每個 session 都從零開始，沒寫進 repo 的脈絡只能自己四處找，既花 token，也可能找到過期的版本；而且 repo 外的脈絡沒有版本，無法跟著分支或 commit 切換。〔原則草稿 §1〕

## 效用的理由

以下出自原則草稿第 2 節；效用本身已定稿在 [goal](new_draft/goal.md)。

| 效用 | 理由 |
|---|---|
| 行為可控 | AI 是沒有記憶的協作者，把規則講清楚，就是管理它的方式。〔原則草稿 §2〕 |
| 接力連續 | 模型的上下文有限，工作也常由不同的 session、模型、機器輪流或同時進行，所以交接程序成為必要。〔原則草稿 §2〕 |
| 人可監督 | 我們通常讓 AI 做很多事之後才看一次 repo，repo 勢必會變凌亂；明確的結構要求，能大幅降低往後整理的負擔。〔原則草稿 §2〕 |
