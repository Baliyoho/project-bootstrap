> 最後更新：2026-11-23

## 為什麼放在 repo 裡

目標開頭與效用「接力連續」的論證。

過去 repo 主要用來放程式碼版本。現在 repo 裡一定會有、而且不可取代的，是和 AI 協作的系統。這套系統包括專案的規範、結構、進度、決策、交接、歷史等，以及相應的驗證程式。

- 系統包含的東西大多不是全新的，很大一部分本來就是 repo 裡慣有的文件，參與者原本就用它們來管理專案、互相協調。這個目的沒有改變，改變的是參與者從人變成 AI agent。
- 參與者改變了，舊配置就不合時宜：人會把進度和協作規則放在腦中，或放在 repo 外的文件。AI 每個 session 都從零開始，沒寫進 repo 的脈絡只能自己四處找，既花 token，也可能找到過期的版本；而且 repo 外的脈絡沒有版本，無法跟著分支或 commit 切換。

## 效用的理由

| 效用 | 理由 |
|---|---|
| 接力連續 | 模型的上下文有限，工作也常由不同的 session、模型、機器輪流或同時進行，所以交接程序成為必要。 |
| 人可監督 | 我們通常讓 AI 做很多事之後才看一次 repo，repo 勢必會變凌亂；明確的結構要求，能大幅降低往後整理的負擔。 |
| 行為可控 | AI 是沒有記憶的協作者，把規則講清楚，就是管理它的方式。 |

## 設計原則的理由

| 對象 | 理由 |
|---|---|
| 原則 1（依主題切分）、原則 4（現況和歷史分開） | 一份文件把歷史、決策和理由放在一起，對人也許方便一次看懂，對 AI 卻會增加 token 成本和搞混的風險。 |
| AGENTS 另訂寫作規範（D12，其餘細則生效時寫進維護手冊） | AGENTS 是唯一保證會被讀到的文件：每個 session 開場整份載入，之後每一輪都佔著上下文。它是原則 5、6 最極端的情況。 |
| AGENTS 寫作規範：擋得住的錯仍留一句規則 | 有些工具不跑 hook。 |
| D10：過期的規則馬上刪 | 過期比沒寫還糟。 |
| 進度另開一份，不寫在 `HANDOFF.md` | `HANDOFF.md` 每個 session 開場都讀，交棒時整份重寫；期別狀態很少變，放在裡面每次交棒都得照抄，抄錯或漏抄就沒了（原則 5、6）。[Cline memory bank](https://docs.cline.bot/prompting/cline-memory-bank) 也把「目前焦點」與「進度」分成兩份。 |

## 不做的事的理由

| 不做的事 | 理由 |
|---|---|
| 不以永久的平台分支維護多份核心 | Git、占用、文件與同步的判斷要共用，平台差異放模組；兩份各自演化會出現一邊會擋、一邊不會擋的不對稱 |
| 不恢復凍結的執行屏障與簽章發布通道 | D9 把執行屏障交給工具；十個以內的專案用不到金鑰鏈 |
| 不以自動信任 hook、繞過沙箱或搬運憑證換取速度 | D9 把權限與沙箱交給工具原生能力；hook 信任不能以快取代替當下觀測 |
| 不一次重寫所有程式、不先導入框架、不預先宣稱跨作業系統或 Python 下限通過 | 框架增加依賴與載入差異，本專案沒有量測支持；Python 下限只有靜態檢查；跨作業系統要等第 3 期（F15） |

## 已知弱點

- **核心依據 E1 只測了 Opus 5.5、單輪對話、macOS。** 這正好是第 1 期的範圍；Codex 與 Windows 排在第 2、3 期才驗。屆時明顯輸的話，依[需求](requirements.md)「驗收」只對那個工具或平台加東西，不推翻常態入口的預算（D11）與內容限制（D12）。
- **F50 沒有任何實測。** 它是必要需求裡唯一 handoff-ab 測不到的；v2 唯一一次遵循量測（2026-11-01，六個收尾 session）漏做的兩個也是它。
- **多輪行為沒有證據。** 已交棒後續聊、使用者中途改主意、上下文壓縮之後還記不記得條件，v2 有不少規則為此而寫，v3 把它們移到參考檔，風險是真的需要時沒人去讀。准入條件適用：出事了、重現了，再加回來。
- **阻擋全部取消是一個實質的保障下修。** 例如祕密外流從「阻擋」變成「偵測」。理由是 v2 的阻擋從來沒有達成過（E2），寫著阻擋而實際沒有，比照實寫偵測更糟；但使用者應該知道現在靠的是模型的判斷加 `.gitignore`。
- **現況索引沒有任何一列是「通過」。** handoff-ab 的情境沒有逐 ID 對應，第 1 期結案也就無法落到個別 ID；各列只寫強度、處置與現行證據。
- **E5 是 Python 單一基準，E6 至 E8 是廠商觀點。** 它們與 E1 同向，但單獨都不足以支撐結論。
