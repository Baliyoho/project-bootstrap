## 怎麼讀

- **編號**：沿用穩定 ID（F 開頭是需求、D 開頭是方案約束），不重編，退役的不列。
- **強度**：以下定義為整合時依 v3 的用法草擬，待確認（見[待決事項](open-questions.md)）。
  - **留痕**：留下紀錄，事後查得到；不保證有人去看。
  - **提示**：在該注意的時機自動提醒，例如開場 hook 印出；不擋。
  - **偵測**：機器查得出違反並報出來；不擋。
  - **阻擋**：用機械手段讓違反的動作做不成。
  - **不變條件**：寫進共用規則、每次都要成立的條件，靠模型遵守。
- **委託**：依 D9 交給工具原生的權限與沙箱，本專案不實作。**想要**：不構成交付義務。其餘都是必要。
- **承擔**：目前由哪個部件做到；空白表示還沒指定。

## 範圍

規模與平台（D8）：

- 兩個工具：Claude Code、Codex。兩個都是每月 20 美元的訂閱，用量有五小時與每週上限。
- 一個使用者、約十個以內的專案、每個專案通常一條線。
- 一次一個 session 是常態。不設計多 agent 並行編排；子代理只在使用者要求時用。
- 不支援 Antigravity 與 Gemini：不是驗收對象，部署形狀不含它們的接線與轉接檔。
- 適用的專案不限寫程式。工作成果不一定在 repo 裡：寫程式時，成果是程式碼；寫企劃書時，成果是文件；叫 AI 修電腦卡頓時，成果是修好的電腦，repo 頂多存放檢測結果。不論哪一種，都要用到協作系統。

不做的事：

- 不以永久的平台分支維護多份核心。
- 不恢復凍結的執行屏障與簽章發布通道。
- 不以自動信任 hook、繞過沙箱或搬運憑證換取速度。
- 不一次重寫所有程式、不先導入框架、不預先宣稱跨作業系統或 Python 下限通過。

## 驗收

- **結果放哪**：handoff-ab 的結果在 [experiments/handoff-ab/](../../experiments/handoff-ab/README.md)。
- **需求達成的證據**是 handoff-ab 式的結果檢查，不是文件裡有對應的句子。每個必要需求至少要有一個「違反時會被機器看出來」的情境，或明寫「只有留痕、不驗」。
- **分期**：每一期的退出條件是該期範圍跑完 handoff-ab 兩輪的十個情境，關鍵檢查的結果不比現行完整版差，並且沒有造成損害的格子。第 1 期另外要在互動 session 驗 F50（handoff-ab 測不到改名）。前一期沒過不開始下一期；後面各期還沒驗的需求一律標未驗證，不沿用前一期的結果。
- **等價**（F14、F15）：同一組情境在另一個工具或作業系統各跑一次，關鍵檢查的結果相同。F14 在第 2 期驗收，F15 在第 3 期驗收（macOS 與 Windows 各跑同一組情境）。某個工具或平台明顯輸時，只對它加一份碰到才讀的參考檔或 hook，不把共用入口加長。
- **新增規則**：准入與對照的驗收方式見 D10、D14。
- **評分器**（F29）：每項關鍵檢查有專屬反例；每個 FAIL 與 INVALID 先人工看原始資料；兩組滿分時要抽查 PASS。
- **未達成要寫出來**（D2、D9）：委託給工具而工具沒提供的，在能力表標「未達成」，不寫成通過。
