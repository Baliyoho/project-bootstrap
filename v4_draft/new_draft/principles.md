# 設計原則

> 最後更新：2026-11-23
> v4 重寫稿，不是現行約束文件。回答「協作系統的文件要怎麼切、怎麼寫，規則怎麼增減，本 repo 的約束文件誰說了算、怎麼改」，是[目標](goal.md)標準 2「文件書寫與架構」的具體內容。為什麼這樣定在[理由與依據](rationale.md)；要做到的需求在[需求](requirements.md)。

**宗旨**：協作系統服務的是人的目的（秩序、整理依據、可溝通），實際讀者大多是 AI。人很少讀，但需要的時候要找得到、讀得懂。

## 原則

1. 一份文件只講一件事（一個主題），可以同時具有多種性質。文件依主題切分，不依讀者切分：人和 AI 讀同一套文件，不為任何一方另寫一套。
2. 做法和名稱能照業界慣例就照；慣例還沒成形的地方，才採用別人的新做法或自己創新。
3. 每個事實只有一個家，其他地方只放連結，不重述。「讀得懂」指理解它所需的知識都有索引可循。每個連結都要說明它指向的內容回答什麼問題。
4. 現況和歷史分開，沒有例外。
   1. 現況文件只寫「現在是什麼」，經過寫進成對的歷史紀錄。
   2. 現況文件不寫「最近改了什麼」。要讓讀者判斷可信程度時，最多寫上次確認仍正確的日期，可附一個指向歷史的連結。
   3. 怕讀者照舊印象做事的地方，寫成現況的規範句（例如「不要把 X 放回來」），不寫成改動紀錄。
5. 依讀取頻率決定長短與分級：
   1. 越常讀的越短。
   2. 在滿足前一項的前提下，盡量把改動頻率不同的內容拆開，但不能因此讓常讀的人得多開檔案。
6. 依錯誤的後果決定維護的仔細程度。後果由三個因素一起判斷：被讀到的頻率、每次讀錯造成的損害、錯誤能不能被檢查擋下。三者各分高、中、低，不算數字。
   1. 損害高的，即使另外兩項低，也不能歸為不用管。
   2. 檢查擋得住的錯，文件本身可以少盯，但那個檢查程式就成了要維護的東西。

## 寫進文件前先問的三個問題

定為檢查清單，不立為原則。

1. AI 自己看一下就知道嗎？是的話不抄進文件，只寫一句指路的話（原則 3：這件事的家在程式碼）。
2. 能寫成程式自動檢查嗎？是的話寫成驗證器的一項檢查（原則 6 第 2 點）。
3. 兩者都不是，才寫進文件。

AGENTS 用的是更嚴的版本，見下一節第 1 點。

## AGENTS 的寫作規範

本 repo 的 `AGENTS.md` 與部署包的 AGENTS 範本都適用。

1. **放進來的門檻**：一句話要同時符合兩個條件。
   1. AI 自己看不出來：讀程式碼或其他文件找不到，或找得到但不會想到要去找。
   2. 不知道就會闖禍：大多數 session 都會碰到，或很少碰到但錯了救不回來。

   不符合的不放；偶爾會用到的，只寫一句「做 X 時讀 Y」。
2. **只放事實與規則**（D12）。不放：專案介紹（README、ARCHITECTURE 的家）、經過與版本來由（歷史紀錄的家）、理由（理由檔的家，只留連結）、逐步程序與判讀表（維護手冊、skill 或其他碰到才讀的參考檔的家，只留連結）、祕密。
3. **能用程式擋的交給程式擋**：驗證器或 hook 擋得住的錯，AGENTS 只留一句規則讓 AI 知道有這條，細節不寫。這一句仍要留。
4. **寫法**：一條只講一件事，用具體的指令與路徑，不寫模糊的話；規則只放在規則清單裡（共用、專用各一份），不散在別的節；用平常語氣，不堆粗體與「絕對」，最重要的幾條可以標一個等級。
5. **順序**：開工前要確認什麼、什麼情況要停 → 不能做的事 → 怎麼驗證算做完 → 碰到才讀的文件索引。
6. **長度**：主要靠第 1 點篩；驗證器另外擋一條寬鬆的上限，防止長度慢慢漲回去。上限見下一節。
7. **維護**：照「規則的增減」。

## 常態入口的預算

每個 session 必載的共用制度 ≤ 40 行；專案的 `AGENTS.md` 全檔 ≤ 100 行；`HANDOFF.md` ≤ 80 行。超過的移到碰到才讀的參考檔（D11）。行數之外要不要另加位元組上限，見[待決事項](open-questions.md)。

## 規則的增減

共用制度與本 repo 自己的規則，增減都照以下條件。

1. **准入**（D10）：同一個錯重複發生，才加一條規則，並登記當時的模型、工具、日期。要進常態入口，還要先有一個極簡版會失敗的情境，加了規則後變成通過；沒有失敗情境的規則不進常態入口。
2. **退場**（D10）：過期的規則馬上刪。換模型後重跑反例，不再重現就移除，理由留在理由檔。
3. **對照**（D14）：新增或保留一條有成本的規則前，用 handoff-ab 的方法比「有它」與「沒有它」；評分只查機器查得到的結果；每個 FAIL 人工看原始資料後才採用。
4. **成本上限**（D15）：單次決策的對照實測 ≤ 24 次模型呼叫、只用訂閱額度、逐批經使用者批准；任一用量窗到 85% 就停；不為制度維護常態並行多個 agent。

## 本 repo 的約束文件

- **哪些是約束文件**：[目標](goal.md)、[需求](requirements.md)、本檔與[實施計畫](roadmap.md)約束本 repo 的所有工作。目標是最高層級的規範，其他文件不得與它牴觸；需求與本檔全文都約束；實施計畫只約束路線、分期、暫緩與取捨，不約束每一步的做法。[理由與依據](rationale.md)、[待決事項](open-questions.md)、[歷史紀錄](history.md)不是約束文件。
- **怎麼改**：要偏離就先改文件。改約束文件要有使用者在聊天中的決定，並在同一個 commit 於歷史紀錄記一筆；AI 可以提案，不能自己改。約束文件都沒寫到的事不算偏離；會新增或改變需求的，先問使用者。
- **現況與歷史**：照原則 4，約束文件直接改寫成現況，條文不附待決事項編號或日期當出處；經過、被改掉而值得留的原文、已決的待決事項，都寫進歷史紀錄。歷史紀錄到下一版時跟這組文件一起封存。
- **歷史的冷熱兩區**：`docs/history/` 是熱歷史：跟現行版本有關、還會增加的紀錄，碰到才讀，讀它不用先經使用者同意，程式可以讀，連結照常檢查。根目錄 `archive/` 是冷區：結案或被取代、不再更動的東西，平常不讀，要回溯先經使用者同意。`archive/docs/` 放文件，程式不讀；`archive/v2-*/` 放退休的 v2 程式與說明，不執行，程式與現況索引都不引用。熱歷史到下一版時連同對應的文件搬進 `archive/docs/`。
- **版本更替**：現行版本是 `AGENTS.md` 的規則連到的那組需求文件。新的穩定版本成為權威（AGENTS 改連新版）之後，現行檔案裡屬於舊版本名稱的一切，包括檔名或資料夾名帶舊版本號的文件與程式、程式裡帶舊版本號的識別字與標籤，都要刪除、封存到 `archive/`，或改成新版本的名稱；現行程式也不得引用 `archive/` 底下以版本號開頭的封存資料夾。文件內文拿舊版本作對照或交代歷史不算；版本號比現行新的草稿不受影響。`verify_bootstrap.py`「版本更替」守。
- **進度不寫在約束文件**：當下這一棒做到哪、整體走到哪一期，寫在 `HANDOFF.md`；逐條需求的實作狀態在[現況索引](../../docs/status.json)。定稿不等於實作完成。
- **需求與計畫的分工**：實施計畫只引用需求的 ID，不重述需求。
- **待決事項怎麼登記**：要使用者決定的事登記在待決事項，每筆寫編號、登記日期、起因、選項、影響的 ID、狀態。決定之後，完整紀錄搬到歷史紀錄的「決策紀錄」，待決清單刪掉，約束文件改成現況，需要時附一個指向歷史紀錄的連結。已決的事項被後來的決定撤銷或改掉一部分時，在舊的那筆標「被取代」或「部分被取代」，並寫明是哪一筆。
